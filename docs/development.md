## Environment variables

The site has two public build-time variables:

- `VITE_WEB3FORMS_ACCESS_KEY`: access key for the Web3Forms quote form. It is invalid when missing, empty or whitespace-only, or equal to the `.env.example` placeholder `your-web3forms-access-key`.
- `VITE_HOME_NEXT`: optional flag (`'true'` or `'false'`) that registers the `noindex` `/next` redesign route in [src/router.tsx](../src/router.tsx) without modifying `src/routeTree.gen.ts`. [vite.config.ts](../vite.config.ts) defaults it to `'true'` during `vite dev` and `'false'` during production builds, so production deployments exclude `/next` unless `VITE_HOME_NEXT=true` is set (for example, during CI design-gate builds).

`scripts/check-public-env.mjs` runs first in `npm run build` and validates only `VITE_WEB3FORMS_ACCESS_KEY`. It loads env the way Vite does (Vite `loadEnv` for mode `production`, prefix `VITE_`), so `process.env` values override `.env` files. When the key is invalid, it exits 1 with a clear message if `CI` or `WORKERS_CI` is set, and otherwise prints a warning and exits 0. Local builds warn and continue; CI builds fail. Cloudflare Workers Builds sets `CI=true` and `WORKERS_CI=1` by default: <https://developers.cloudflare.com/workers/ci-cd/builds/configuration/>.

`src/lib/public-env.ts` exports `getWeb3FormsAccessKey(): string | undefined` (undefined when the key is invalid) and `PLACEHOLDER_WEB3FORMS_ACCESS_KEY`. The release deploy (`deploy-production.yml`) and CI (`ci.yml`) read the key from the repository variable `VITE_WEB3FORMS_ACCESS_KEY`. It is a public key, never a secret, and the `production` environment holds no copy. Workers Builds builds need the key too: they pass under `WORKERS_CI`, and the env check fails them without it. Its variable name there is not recorded.

## Tests

Vitest 5.1.0 with the default environment `node` and globals off. Files that need a DOM opt in per file with a `// @vitest-environment jsdom` docblock comment and use jsdom with `@testing-library/react` and `@testing-library/dom`. There is no `@testing-library/jest-dom`. Tests never submit the quote form and never make network calls to Web3Forms.

## Lint and format

- `.oxlintrc.json`: oxlint with the react and typescript plugins; correctness rules are errors.
- `.oxfmtrc.json`: oxfmt with print width 80, two-space indentation, no semicolons, single quotes, LF line endings.

Both configs ignore `src/routeTree.gen.ts` and `dist`; the oxfmt config also ignores `package-lock.json`.

## Continuous integration

Three workflows run on every pull request to `main`, and CI also runs on pushes to `main`. All live under `.github/workflows/` and pin their actions by full commit SHA; GitHub also enforces it (`sha_pinning_required`, #56). The one exception is actionlint in `ci.yml`, a version- and checksum-pinned binary that is bumped by hand from the release's `checksums.txt` (Dependabot cannot update it).

- `ci.yml` (`Verify`): reviews dependency changes (pull requests only), lints the workflow files with actionlint, then installs with `npm ci` and runs `npm run verify` (format:check, lint, typecheck, test, build) on ubuntu-latest using the Node version from `.nvmrc`. It reads the public build variable from the `VITE_WEB3FORMS_ACCESS_KEY` repository variable, which the maintainer sets for CI builds; `deploy-production.yml` reads the same variable. The build's env check fails in CI when the key is missing. Dependabot runs receive the repository variable (observed on #30 to #34); fork PR runs are unverified and may not, in which case Verify fails at the env check.
  - Dependency review blocks on advisories of any severity in runtime and development dependencies, because the build and deploy tooling (vite, wrangler, vitest, tailwind, jsdom) is development scope. There is no licence policy: an allow-list would fail on licence-string variants in transitive development dependencies and cost a sole maintainer upkeep, and the check exists to block vulnerabilities.
  - actionlint runs shellcheck on every `run:` block. A shellcheck change on the runner image can surface new findings with no repo change. The `shellcheck disable=SC2016` comments in the other workflows cover literal markdown backticks inside `printf` formats.
- `pr-metadata.yml` (`PR metadata`): runs `scripts/pr-metadata.mjs` from the base commit, so a PR cannot change the rules it is checked against. It validates the PR title, labels, closing issue and ticket exemptions, and reports failures as annotations. A validator change applies to each open PR on its next event after the change merges.
- `design-gate.yml` (`Design gate`, #92): runs on pull requests to `main` only, and is not a required check while the redesign is built. It builds with `VITE_HOME_NEXT=true`, serves `dist/` with the pinned wrangler in local dev mode (no Cloudflare login), asserts the `Content-Security-Policy` header from `public/_headers` is applied, then runs the headless-Chrome probe in `scripts/design-gates/` against `/next` with the runner's preinstalled Chrome. The job fails on a `fail` or `unknown` gate verdict; while `/next` is still being built, gates whose subject is not on the page yet report `skipped` and never fail the run. The report (`probe.md`/`probe.json`) and the screenshots (1440, 1280 and 390 wide, plus the six reflow widths) upload as the `design-gate-report` artifact, on failure too. Locally: `VITE_HOME_NEXT=true npm run build`, then `node scripts/design-gates/serve.mjs`.

The `main` ruleset requires both checks and up-to-date branches. CodeQL default setup also runs on pull requests (dashboard-configured, not a workflow file).

Dependabot (`.github/dependabot.yml`) opens weekly update PRs for npm and GitHub Actions dependencies, limited to 5 open PRs each. A 7-day cooldown delays version updates after a release (security updates are not delayed). Minor and patch updates are grouped into one PR per ecosystem; major updates stay individual PRs, so one breaking major cannot hold back the safe updates. Because development scope is included, a grouped PR that brings in any advisory fails `Verify` and holds the whole group. Dependabot PRs carry the `dependencies`, `type:maintenance` and `area:dependencies` labels and a `build(...)` title prefix so they pass the `PR metadata` check under the bot exemption.

## Releases

Release Please (`.github/workflows/release-please.yml`) runs on every push to `main`. It mints a token for the `winzelle-release` GitHub App (repository variable `RELEASE_APP_CLIENT_ID`, `release` environment secret `RELEASE_APP_PRIVATE_KEY`) and runs `googleapis/release-please-action` against `release-please-config.json` and `.release-please-manifest.json`. The key is readable only by jobs on `main` through the environment's branch policy, and the job sets `deployment: false`, so it creates no deployment records. The App token does the writing; the workflow's own `GITHUB_TOKEN` stays read-only.

- Release PRs come from `winzelle-release[bot]` and carry the labels `autorelease: pending`, `automated`, `type:maintenance` and `area:release`, so they pass the `PR metadata` check under the `automated` ticket exemption. Merging a release PR tags `v<version>` and relabels the PR `autorelease: tagged`. The tag ruleset allows only the App to create `v*` tags, and nobody to update or delete them. The labels must not be edited by hand: Release Please finds its PR by all four labels, and changing them would make it open a duplicate.
- Versioning is pre-1.0: `bump-minor-pre-major` turns breaking changes into a minor bump. The manifest starts at `0.0.0` and `initial-version: "0.1.0"` in the config makes the first release PR propose exactly 0.1.0; the option is inert once a release exists, so nothing is pinned for later releases.
- The first `PR metadata` run on a release PR can fail or be cancelled before the labels land; the `labeled` re-run settles it.
- Publishing a release is the only production deploy path (W11, #13). `.github/workflows/deploy-production.yml` triggers on release publication (prereleases excluded), runs in the `production` environment (maintainer approval), builds the tag, deploys with `wrangler deploy`, and smoke tests the result. On deploy or smoke failure it rolls back to the previously live version and smoke tests the rollback; the run stays failed either way. The job summary and the release notes record tag, commit, Worker version IDs, actor and timestamp for every successful deploy. Re-running the workflow for the same release redeploys that tag; tags are never moved or reused. Merging a release PR publishes a release, so only the maintainer merges release PRs.
- Since 2026-11-14 (#13), Workers Builds runs `npx wrangler versions upload` on `main` only, so a merge uploads a Worker version and moves no traffic. Non-production branch builds are off (#56), so PRs show no `Workers Builds` check (observed on #70 and #73).
- `.github/workflows/rollback.yml` (Actions → Rollback production) restores a named Worker version — or by default the most recent deployment that was not itself rolled back from — in the `production` environment and smoke tests the result; it moves production with the same maintainer approval as a release deploy. The runbook is [docs/rollback.md](rollback.md).
- The `production` GitHub environment requires review by `@WianVDM` and limits deployments to `v*` tags and `main`. It holds the environment secret `CLOUDFLARE_API_TOKEN` (account-scoped, Workers Scripts write only) and the environment variable `CLOUDFLARE_ACCOUNT_ID`. Names only; values never enter the repository.
- `.github/workflows/cloudflare-check.yml` runs on `workflow_dispatch` only, inside the `production` environment, and is read-only. It first fails fast if the token is missing, then calls the token verify API and fails unless the token is active, then lists deployments as JSON and prints only each deployment's ID, created-on time, source and version IDs. It prints no emails and no account names, because the repo is public. It collects W10 evidence; `deploy-production.yml` and `rollback.yml` reuse its environment wiring.

## Security headers

`public/_headers` sets the response headers for the Worker's static assets (Vite copies `public/` into `dist/`): a Content-Security-Policy, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`, because a mail host exists; no `preload`). Content-hashed `/assets/*` also gets `Cache-Control: public, max-age=31536000, immutable`; `index.html` keeps Cloudflare's default revalidation.

- CSP allow-list: `https://fonts.googleapis.com` for the Google Fonts stylesheet, `'self'` in `font-src` for self-hosted fonts under `public/fonts/` plus `https://fonts.gstatic.com` for the current page's Google font files, `https://api.web3forms.com` for the quote form `fetch`, and `https://static.cloudflareinsights.com/beacon.min.js/` in `script-src` for Cloudflare Web Analytics. Cloudflare injects the beacon tag into HTML for browser requests only, so `curl` and `wrangler dev` don't show it; that is why #57's checks missed it (found after `v0.2.0`, #69). The beacon reports to the same-origin `/cdn-cgi/rum`, already covered by `connect-src 'self'`. The source is a path prefix because the script path is versioned (`/beacon.min.js/<version>`); a bare `/beacon.min.js` would not match. Everything else is same-origin. `object-src 'none'`, `frame-ancestors 'none'` and `form-action 'none'` are intentional: the form posts with `fetch` after `preventDefault()`, so a native submit is blocked.
- Changing the CSP: edit `public/_headers`, build with a dummy `VITE_WEB3FORMS_ACCESS_KEY` (without a key Vite drops the Web3Forms `fetch`), serve `dist/` with a fresh `npx wrangler dev` process, read the full header values with `curl -sI`, and load the site in a browser with the console open. For a risky change, trial it as `Content-Security-Policy-Report-Only` first.
- `node scripts/smoke.mjs <baseUrl> --expect-headers` asserts the full set on `/` and the CSP plus `nosniff` on the SPA fallback, and that the main module script has exactly one `max-age` of at least a year plus `immutable`. The deploy smoke and `Production smoke` pass the flag. The rollback smokes do not, so a rollback to a version without headers can still pass. The smoke reads headers only and cannot see CSP breakage in a browser.
- Known limit: `_headers` cannot tell a real `/assets/*` file from a missing one, so with the SPA fallback a missing chunk returns 200 HTML carrying the immutable header. After a rollback, a tab holding a newer `index.html` can cache that HTML under a real chunk hash for a year, and the chunk then fails to load for that visitor until the cache entry goes. `nosniff` makes the browser reject the HTML as script. No mitigation exists; this is a known limit.
- HSTS survives rollback: browsers keep the policy after `Rollback production`, and only a later `max-age=0` clears it. The risk is small (Always Use HTTPS is on, Cloudflare manages the certificate, no `includeSubDomains`), so the one-year `max-age` stays.

## Monitoring

Proportional and free (W13, #15): a smoke run by hand plus failure issues. There is no scheduled check: GitHub never fired this repository's `schedule` trigger, so it was removed (#81). No monitoring platform, and nothing submits the quote form.

- `.github/workflows/production-smoke.yml` (`Production smoke`) runs `scripts/smoke.mjs` against `https://winzelle.co.za` when dispatched from Actions → Production smoke → Run workflow. It is read-only and touches neither the deployment nor the form recipient. Run it after a Cloudflare dashboard change and periodically between releases.
- `Production smoke` asserts the security headers (`--expect-headers`). After a rollback to a version without them, its next run opens an alert, which closes when a `Production smoke` run passes after a fixed release ships.
- `Production smoke` also asserts the www redirect (`--expect-www-redirect`): `https://www.winzelle.co.za/smoke-www-check?probe=1` must answer 301 with `Location: https://winzelle.co.za/smoke-www-check?probe=1`. #43 specifies 301, so 302, 307 and 308 fail. The check runs only when the flag is set and the base URL is `https://winzelle.co.za`. Only `Production smoke` passes the flag; deploy and rollback smokes do not, so a broken zone Redirect Rule cannot fail a good deploy and trigger an auto-rollback. The trade-off: a broken rule surfaces only at the next `Production smoke` run, not at release time.
- `.github/workflows/failure-alert.yml` (`Failure alert`) watches `Production smoke`, `Deploy production`, `Rollback production` and `Release Please`. Release deploys are triggered by `winzelle-release[bot]`, so GitHub's failed-run emails go to the bot; an issue notifies the maintainer instead. `workflow_run` runs the file from `main`, so edits apply only after they merge.
- Alert lifecycle: a run that ends `failure`, `timed_out`, `startup_failure` or `cancelled` opens `Production alert: <workflow name>`, assigned to `@WianVDM`. Smoke alerts carry `type:bug` and `area:ci`; deploy, rollback and Release Please alerts carry `type:bug` and `area:release`. While the issue is open, further failures of the same workflow add a comment that mentions `@WianVDM`. `cancelled` alerts on purpose for deploy and rollback: a cancelled deploy may have left an auto-rollback, and a queued rollback can be superseded. `Release Please` is the exception: its single concurrency group cancels a pending run when a newer push queues, so a `cancelled` run is skipped. That also hides a run cancelled by hand and possibly a run that hits `timeout-minutes`; whether GitHub records a timeout as `cancelled` is unverified. A Release Please alert omits the rollback text; a later successful push run closes it. `action_required`, `stale`, `skipped` and `neutral` do nothing.
- Recovery: a `success` closes the open alert with a "recovered" comment. For `Production smoke` only a run whose title is exactly `Production smoke (https://winzelle.co.za)` counts, because `run-name` carries the target; a pass against another origin leaves the alert open. A failure against any target still opens or comments, with the target shown.
- Deduplication: the alert is found by its exact title and the `type:bug` label. Editing either while it is open breaks deduplication and a second issue opens. Alert issues come from automation, so they are exempt from the issue-form rule and carry no priority or parent.
- Controlled test (a), smoke: run Production smoke with `base_url` `https://smoke-failure.invalid`. Expect `Production alert: Production smoke` with the target shown. Then run it again with the default URL; that run closes the issue with the "recovered" comment. Observed 2026-11-14: runs 43612504638 (failed) and 43612639176 (passed); alert #54 opened and recovered (#15).
- Controlled test (b), rollback: dispatch `Rollback production` with a throwaway reason and reject the `production` approval, so production stays untouched. Expect `Production alert: Rollback production`. Observed 2026-11-14: the conclusion of a rejected approval is `failure` (run 43613451294, alert #55, production unchanged; #15). A later successful rollback run would close the issue; otherwise close it by hand after recording the evidence.
- Residual risks: `Failure alert` does not monitor itself, so check Actions → Failure alert after the controlled tests and after any real failure. A prerelease deploy run is expected to conclude `skipped` (job-level `if`) and so be ignored, but that is unverified until observed.
- Cloudflare Notifications, observed in the dashboard (Notifications → Add) on 2026-11-14. "Availability & performance" lists Health Checks status, Load Balancing health, Pool enablement, Failing Logpush Job Disabled, Network flow auto advertisement, Pages deployment updates, Stream live alerts, Passive Origin Monitoring, Tunnel creation/deletion and Tunnel health. "Certificates & access" lists Advanced Certificate, Expiring Access Service Token, Access mTLS certificate expiration, Hostname and Zone Authenticated Origin Pulls certificate expiration, mTLS Certificate Store expiration and SSL for SaaS custom hostnames. None covers Workers deploys or errors ("Pages deployment updates" is Pages only), and none covers API token expiry ("Expiring Access Service Token" is for Cloudflare Access service tokens). `CLOUDFLARE_API_TOKEN` has no expiry (maintainer, #2 comment, 2026-11-14), so no reminder exists. ## Accepted and open risks

Accepted (maintainer decisions on #2, #15 and #56):

- `npm ci` runs in all three `production` jobs, and the deploy job also builds, next to the Cloudflare token.
- Fork-PR credential isolation is unobserved: no fork PR has existed, the maintainer is the only contributor, and GitHub's Terms B.3 apply.
- The automatic rollback is implemented but unobserved, because forcing a bad release was rejected. The manual rollback was observed (#13).
- Immutable releases are declined.
- DNSSEC is declined.
- Wildcard DNS `*` stays proxied to the old origin for mail auto-setup, webmail and cPanel; replacing it with explicit records is possible later (#56 comment 6891118996).
- SSL/TLS mode is [Full](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full/), not strict: Cloudflare encrypts to the old origin but does not validate its certificate. Strict was not chosen because the provider's certificate does not cover the mail auto-setup hosts; it is expected to answer 526, not tested (#56 comment 6891546468).
- No scheduled monitoring: GitHub never fired this repository's `schedule` trigger (the 04:17 UTC daily slot and two one-shot tests on 2026-11-15, the second after re-registering the workflow; #15 comment 6894340404), so the schedule was removed (#81). `Production smoke` runs by hand, and the deploy and rollback smokes still run on every release and rollback. A site that breaks between releases surfaces only at the next manual smoke.

Open or residual items (not decisions):

- DMARC is `p=none` (monitor-only) and SPF ends `~all` (#56).
- `CLOUDFLARE_API_TOKEN` is account-scoped and never expires (#2 comment 6880778486).
- Web3Forms free-plan limits: see the Web3Forms paragraph under Hosting records and the zero-paid rule.
- The Cloudflare MCP grant is read-only but not least privilege: the 'Read only' template includes data reads (KV, R2, logs, PII) (#63 comment 6891546109). `wrangler.toml` binds no KV, R2 or D1 today. A scoped API token would narrow it.

## Agent access to Cloudflare

Agents may read Cloudflare state through the official Cloudflare API MCP server (#63). Writes are out of policy (`CLAUDE.md`). The server is configured per machine in local scope; nothing is tracked. The OAuth grant stays in the maintainer's client and never enters the repository.

- Connect: register the server with `claude mcp add --scope local --transport http cloudflare https://mcp.cloudflare.com/mcp`, then run `claude mcp login cloudflare` in an interactive terminal. Run both commands with the same `CLAUDE_CONFIG_DIR` value the agent client runs with; leave it unset if the client uses the default. That directory can differ from the one a plain terminal `claude` uses (observed 2026-11-15). Login refuses without a TTY ("stdin isn't a terminal", observed 2026-11-15), so an agent cannot complete it. Confirm with `claude mcp get cloudflare`, which reported "Local config (private to you in this project)" on 2026-11-15. Start a new agent session afterwards. An agent session loaded the tools and ran reads after the login on 2026-11-15 (#63 comment 6891403888); whether a session already running picks them up is unverified.
- Scope: local means this project path only, private, stored in `.claude.json` (in `$CLAUDE_CONFIG_DIR` when set, otherwise in the home directory) under this project's path. A second clone or worktree at a different path needs its own setup; whether Claude Code maps a worktree to the main repo path is unknown. An older clone that still has the project MCP file: delete it there; the local entry takes precedence anyway.
- Consent screen: select only the Winzelle account, open Edit Permissions and choose "Read only". That template covers optional scopes; required scopes cannot be deselected (Cloudflare docs, "Authorizing an application", and the 2026-04-14 and 2026-08-22 changelogs). Record every selected scope name verbatim, required ones included, and no identifiers. The authorization request asks for scopes `user:read account:read offline_access` (observed 2026-11-15).
- Stop rule: if the consent screen offers no read-only selection, or a required scope is write-capable, do not authorize. The maintainer decides the next step.
- Read-only evidence: the maintainer-observed permission list. No write is attempted, because one would be out of policy. Observed 2026-11-15: no permission name contains Write, Edit or Admin; the template grants every read, data reads included, so the grant is read-only but not least privilege (#63 comment 6891546109). The check rests on the permission list, not on an observed refusal.
- Contributors: clones have no server configured, so nothing loads.
- Revoke: at Cloudflare, Profile, Access Management, Connected Applications, then Revoke. Then clear local state with `claude mcp logout cloudflare`, then `claude mcp remove cloudflare --scope local`. Removing the server locally does not revoke the grant at Cloudflare. The Connected Applications page and the grant's permission list were observed on 2026-11-15 (#63); revoking is unverified.
- Failure: on an auth error the agent stops and asks the maintainer, and never requests broader access. If the server is down, the check is listed as Unexecuted.
- Use: agents verify settings such as #56, #43 and #58 (Always Use HTTPS, minimum TLS, the www redirect rule, zone TXT records, Workers Builds branch builds). Reads already made: zone Worker routes, wildcard DNS, Workers Builds triggers, and Web Analytics page loads (#63, #69). Extra, outside #63's test plan: the Worker's `workers.dev` and preview URLs are disabled. Reports carry values and pass/fail only, with no hostnames, account IDs or binding values on GitHub.

Server docs: https://developers.cloudflare.com/agents/model-context-protocol/mcp-servers-for-cloudflare/

## Line endings on Windows
